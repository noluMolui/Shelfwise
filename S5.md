# S5: Stock Movements

## What was built

Phase 5 includes the stock history screen (S5) and the connected record-movement form (S6):

- `/stock` lists stock movements newest first, with product name, SKU, movement type, quantity, recording user, and South African Standard Time dates.
- Movement type and From/To date filters narrow the list. Results are paginated in batches of 20.
- S5 includes responsive layouts and loading, empty, error, offline/cached-data, and newly-recorded success states.
- `/stock/new` lets a signed-in business owner or staff member select an active product, choose Incoming or Outgoing, enter a whole-number quantity, and optionally add a note.
- The form displays the selected product's current stock and checks outgoing quantities before saving. The database repeats the stock check atomically, so concurrent outgoing movements cannot take stock below zero.
- Successful saves return to S5, refresh the relevant data, and show a success message.
- Added stock-movement database types, API operations, quantity validation, and UI tests.

## Database and access control

The repository did not contain the stock-movement table expected by the implementation plan. Added [the migration](./supabase/migrations/20261112190000_stock_movements.sql), which creates the table, indexes, row-level security policies, and database triggers.

- Members can read movements for their own business.
- Owners and staff can record movements only for their own business, with the caller recorded as the actor.
- The database trigger locks the product row, rejects archived products and insufficient stock, and updates product quantity in the same transaction as the movement.
- Movement history cannot be updated or deleted.

## What is not verified yet

The code and local checks are in place, but the migration has **not** been applied to a Supabase database, and real sign-in or stock changes have **not** been tested against live data. This workspace has no configured Supabase project or `.env` credentials. The automated tests do not replace the planned database-integration, end-to-end, and owner/staff manual checks.

In practical terms: the app can compile and its local tests pass, but its stock screens cannot read or save real inventory until a Supabase project is configured and the migration is applied there. This does not mean the screens are missing or preview-only.

## Why the browser may show `/login`

`/stock` and `/stock/new` require an authenticated user with a business profile. If someone opens either route while signed out, the existing route guard redirects to `/login`; that is expected access control, not a stock-screen error. To view the live screens, configure Supabase and sign in with an account that has a profile.

## Before shipping

1. Configure the Supabase URL and public anon key in the local/deployment environment.
2. Apply the stock-movement migration to the target database.
3. Run the planned database and end-to-end tests, then manually verify incoming/outgoing movements as both an owner and a staff member.
